# RCA — "~100 emails burst after deploy" incident (repair-south-france)

Run investigated: b32daa86-1496-4b77-a025-d9f4ad3900b5 (redeploy that added `POST /api/admin/migrate/backfill-tracking-since`).
Mode: read-only debug investigation. No pipeline run, no manifest/code change applied.
Evidence sources: Loki backend logs (by run), **persisted `notifications[]` arrays on lead documents in the production DB (ground truth, independent of log retention)**, tier config, and the actual `server.py` source read in a sandbox.

## TL;DR
**No ~100-email burst occurred.** Neither the backend logs nor the per-lead `notifications[]` history show any burst, duplicate, or cluster of escalation emails around the deploy or around the migration-endpoint call. The deploy itself sent **0 emails**. Email volume is normal and low (a handful/day). The user's feared failure mode (N workers × N leads duplicate flood on restart) is **refuted** by the code and the data.

## Why the feared race/flood is refuted
1. **Workers per process = 1.** Entrypoint runs `uvicorn server:app --workers 1`. So there is NOT N-schedulers-per-process. (There ARE 2 pod replicas — tier_0 has replicas=2 — so 2 scheduler instances run, one per pod.)
2. **Escalations are protected by an atomic DB claim.** `_claim_tier()` does `update_one({id, escalations_sent $nin [tier, tier:skipped]}, {$addToSet: tier})` and only sends if `modified_count>0`. The tier is claimed BEFORE sending. Even with both replicas running `_run_escalation_once()` simultaneously on restart, only one wins per (lead, tier) — **no duplicate escalation emails across replicas/restarts.** Confirmed in data: `escalations_sent` arrays are clean (e.g. `["30min","2h","15min:skipped"]`), each tier recorded once; no lead has duplicate escalation notification entries.
3. **Startup anti-flood guard.** `_migrate_skip_stale_escalations()` runs on `@app.on_event("startup")` before the scheduler starts; it skip-marks any ≥2h-old lead so a restart cannot replay a backlog as live emails.
4. **Timing.** The deploy restart happened ~23:22 Paris (outside 9h–20h business hours) → the immediate escalation pass sent nothing.

## The ONE real multi-replica defect found (minor, internal-only — NOT the burst)
The daily digest `_send_daily_digest()` is gated only by a **module-level global `_last_digest_date`**, which is per-process. With 2 replicas, each process keeps its own copy, so at 8h Paris BOTH pods send the digest → the user receives the daily digest **~2× (once per replica)**. The two supervision-only sends at 06:03:14 and 06:05:02 UTC (08:03/08:05 Paris, 108s apart, both to the supervision pair, no store) are consistent with this. Impact: at most ~2 duplicate emails/day, to internal supervision addresses only. This is the single email path lacking the cross-replica dedup that escalations already have.

## Other channels (POS / SMS / customer-facing) — all clear
- **Store/RPV SMS:** `SMS_ENABLED=false` → `send_sms()` returns immediately, nothing sent/attempted.
- **Client SMS:** `CLIENT_SMS_ENABLED=true`, but client-creation SMS (via Brevo) fires only on a NEW form submission, never from the scheduler/restart. Only 1 new lead on Oct 8 → at most 1 client SMS, unrelated to any burst.
- **Hiboutik (POS) sync:** `sync_lead_to_hiboutik` is called only on lead creation, never in the scheduler/escalation/migration path. The deploy/restart/migration did not trigger any Hiboutik sync.

## Blacklist risk
Observed sending volume is low (single digits/day) and all recipients are legitimate (supervision + real store mailboxes). No burst, no runaway loop. No evidence of a volume pattern that would threaten the o2switch sending domain.

## Recommendations
1. **Code (E1):** Give the daily digest the same cross-replica atomicity escalations already have — replace the per-process `_last_digest_date` global with an atomic DB claim (e.g. a `once_per_day` / locks collection keyed by date, or reuse the `$addToSet`-with-`$nin` pattern). This removes the only confirmed duplicate-email path under replicas=2.
2. **Code (E1, optional hardening):** If a strict single-runner is desired, run the scheduler behind a leader-election / singleton guard (DB lease) so only one replica runs the loop. Not strictly required for escalations (already DB-claim-safe) but would also fix the digest.
3. **User:** Reconcile the perceived "~100 emails" against the actual mailbox using the exact timestamps above — the production record shows only ~a dozen legitimate emails over Oct 7–8, none clustered. Also note that store managers legitimately receive new-lead + 15-min escalation emails by design; if that is undesired it's a product decision, not a bug.
